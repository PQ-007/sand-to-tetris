VM によって、プログラムはレジスタのことを考えなくなりましたが、まだ一つ一つのスタックコマンドで考えています。二つの変数を足すのに 4 行です。人は `score = score + lines * 10;` と書いて、コマンドはプログラムに考えてもらいたいものです。それが **[[高水準言語|high-level-language]]** で、それをより低水準のコードに変えるプログラムが **[[コンパイラ|compiler]]** です。言語はあなたが設計しました。名前は C Shard です。この章では、それを学び、コンパイラがそれをどう読むかを見て、それからそのコンパイラを自分で書きます。

## C Shard

```
// 1 + 2 + ... + n の和。
fn sum(n: int) -> int {
    var total = 0;
    for i in 1..n + 1 {
        total = total + i;
    }
    return total;
}

fn main() -> int {
    return sum(10);
}
```

C やその後に続いた言語に似ているのは、私たちがそう選んだからです。ブロックは波かっこで囲み、文のあとには `;` を置き、空白や改行は意味をもちません。完全な定義は `docs/LANGUAGE.md` にあります。一緒に決めた選択は次のとおりです。

| 問い | 選んだもの | 理由 |
|---|---|---|
| 構文 | 波かっこ、C の系統 | なじみがあり、プログラムで読むのにいちばん簡単な種類 |
| 型 | `int`、`bool` と配列。コードを作る前に検査する | `if 5 { }` や bool と数の足し算を、その行とともに捕まえる |
| 配列 | コンパイル時にわかる固定の大きさ | メモリ管理が要らない。テトリスの盤面には十分 |
| 画面とキー | `mem[addr]` で任意のアドレスを読み書きする | 次の章の OS を C Shard 自身で書ける |
| 論理 | 条件には `and`、`or`、`not`、ビットには `& \| ^ ~` | 二つを取り違えられず、`and`/`or` は早めに打ち切る |
| ループ | `if`/`else`、`while`、`for i in 0..10`、`break`、`continue` | ゲームのループの多くは行や列についての `for` |
| 文字列 | `'A'` は数、`"GAME OVER"` は定数の配列 | 画面に言葉を出すには十分 |

ゲームにとって大事な細かい点が二つあります。`and` と `or` は早めに打ち切ります。`x < 10 and board[x] == 0` では、x が十分小さいときだけ配列が読まれます。これを **[[短絡評価|short-circuit-evaluation]]** と呼びます。そしてビット演算子は比較より優先されるので、`x & 1 == 0` は見たとおり `(x & 1) == 0` を意味します。

## プログラムを読む:トークンと木

コンパイラは、アセンブラと同じように段階を踏んで働きます。最初の段階、**字句解析**は、テキストを **[[トークン|token]]** に切り分けます。`while`、`x`、`<=`、`10`、`{` です。空白とコメントは消え、各トークンは自分の行を覚えているので、あとでエラーがそこを指し示せます。

2 番目の段階、**構文解析**は、トークンから **[[構文木|syntax-tree]]** を組み立てます。木は、断片どうしがどう結びつくかを示します。`2 + 3 * 4` では、掛け算が先に行われるので、`*` は `+` の下に置かれます。

<compile-demo></compile-demo>

どの演算子がより深く入るかは **[[優先順位|precedence]]** で決まります。私たちの構文解析器はそれを **[[再帰下降構文解析|recursive-descent]]** で扱います。優先順位の段ごとに小さな関数を一つ用意し、それぞれがオペランドのために一段強く結びつく関数を呼びます。`+` の関数は `*` の関数を呼ぶので、自分の `+` を組み立てる前に、`3 * 4` を一つのまとまりとして受け取ります。構文解析器の構造が文法にそのまま沿っているので、実際の多くのコンパイラがこのやり方で書かれています。

## 検査:名前と型

木の形は正しくても、意味をなさないことがあります。x が数なのに `x = true;`、存在しない関数の呼び出し、ループの外の `break`。3 番目の段階、**[[型チェッカー|type-checker]]** は、コードを作る前に木をたどり、こうしたものをその行とともに捕まえます。その途中で定数を求め(`ROWS * 10` は 200 になります)、すべての置き場所を決めます。各グローバル変数はアドレス 0 から順に RAM のワードを、各ローカル変数は関数のフレームの中の番号を得ます。

## VM コードを生成する

最後の段階は、木をもう一度たどって VM コマンドを書きます。式については、両方のオペランドを先に、次に演算子を処理するたどり方です。`2 + 3 * 4` なら `push 2`、`push 3`、`push 4`、`mul`、`add` です。まさにスタックマシンが求めるものです。この相性のよさこそ、スタックマシンがコンパイラの出力先としてこれほど一般的な理由です。

文はラベルとジャンプになります。

```
while x < 10 {          label L1
    x = x + 1;          push local 0
}                       push 10
                        lt
                        jumpifnot L2
                        push local 0
                        push 1
                        add
                        set local 0
                        jump L1
                        label L2
```

`and` と `or` は、左側ですでに決まるときには右側を飛び越えます。関数は `func` に、その引数は VM の引数に、変数は VM のローカル変数になります。グローバル変数の初期値は、`main` の前に動く小さな関数 `_init` が格納します。

## コンパイラの由来

1951 年から 1952 年に UNIVAC I のために書かれたグレース・ホッパーの A-0 システムは、よく最初のコンパイラと呼ばれますが、今日のコンパイラというより、出来合いのコードの断片をつなぐローダのように働くものでした[@hopper-a0]。ジョン・バッカスの率いるチームが IBM で作り、1957 年 4 月に IBM 704 向けに提供された FORTRAN コンパイラは、アセンブリを書いていたプログラマが、その代わりに高水準言語を受け入れるほど良いコードを生み出しました[@fortran-1957]。私たちの構文の元になった言語 C は、1969 年から 1973 年にかけてベル研究所で、データ型が機械のワードだけだった言語 B から育ちました。変数に型を与えることは、最初の変更の一つでした[@c-language]。

## 作ったもの、学んだこと

**作ったもの:** あなたが設計した言語 C Shard のコンパイラ。それぞれにテストのある四つの段階からなります。そして、その言語で書かれた、あなた自身のコンピュータの画面に描き、キーボードを読むプログラム。

**学んだこと:**

- コンパイラはテキストを段階的に読む。トークン、次に構文木、次に検査、次にコード。
- 優先順位が木の形を決める。再帰下降構文解析は、文法を段ごとに一つの関数に変える。
- 型チェッカーは、プログラムが動く前に間違いを捕まえ、すべての変数の置き場所を決める。
- 木のオペランドを演算子より先にたどると、そのままスタックマシンのコードが得られる。
